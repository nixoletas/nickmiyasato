## The problem

Organising a weekly pickup football match in Brazil runs on a broken ritual: someone posts a numbered list in the WhatsApp group, the next person copies the whole thing, appends their name, and re-sends it. Twenty messages later there are three competing versions of the list, two people booked for the same slot, and nobody is sure where the pitch actually is.

It is a coordination problem dressed up as a text-formatting problem.

## What I built

A shareable event page. The organiser creates an event with a date and a location; everyone else opens one link, sees the pitch on a map, and adds their own name. The list has exactly one canonical version, and it updates for everyone at once.

The last step matters more than it looks: the organiser can copy the finished list back to the clipboard in the same numbered format the group already expects. The tool meets the habit where it is instead of demanding people abandon it.

## Technical decisions

**Supabase over a hand-rolled backend.** The whole product is a shared list with auth and row-level access rules. Postgres with RLS covers that directly — auth, database, and authorisation policy in one place, with no API layer whose only job would be to forward CRUD.

**Google Maps instead of a text address field.** "Campo do Zé, near the bakery" is not an address. Attaching a real pin removed the single most common follow-up question in every group.

**Anonymous participation by design.** Requiring a signup before you can add your name to a football list would have killed adoption instantly. Only the organiser authenticates; guests just need the link.

**Started from a Lovable scaffold.** The first screens came out of an AI code generator. That got a clickable shell in front of people fast — everything past that point (data model, RLS policies, Maps integration, Supabase Auth, deploy, custom domain) I built and own.

## Where it stands

Live at [futevento.com.br](https://futevento.com.br) on its own domain, in real use by the groups it was built for.
